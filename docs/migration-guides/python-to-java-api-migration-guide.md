# Python -> Java API 迁移通用 Guide

这是一份面向后续所有页面迁移的通用指南，不绑定某个具体页面。
目标不是“把代码搬过去”，而是“把数据契约、分层边界、口径一致性和可维护性一起迁过去”。

## 1. 先理解问题为什么会发生

### 1.1 迁移时最容易犯的错

很多迁移失败，不是实现能力不够，而是默认把“能跑”当成了“迁移完成”。

常见误区：
- 先把接口跑起来，再回头补契约
- 先让前端显示出来，再回头补数据口径
- 先用 `Map` / `JsonNode` 顶住，再说后面重构
- 先把 SQL 写进去，再说后面分层

这些做法短期有效，长期会把系统带进“能用但不可维护”的状态。

### 1.2 问题的根因

迁移时真正难的不是代码量，而是四类边界：
- 数据边界：原始数据、派生数据、展示数据是否分清
- 责任边界：谁负责采集，谁负责计算，谁负责服务
- 契约边界：接口字段是否稳定、可读、可追溯
- 口径边界：同一指标是否所有入口都取同一种定义

只要这些边界不先定，后面一定会出现“看起来对了，实际上错了”的情况。

## 2. 迁移的核心原则

### 2.1 先定契约，再写实现

先定义 DTO / Request / Response，再写服务逻辑。

为什么：
- 契约先行会逼你想清楚字段来源
- 前后端可以并行推进
- 后期改动只会影响少量边界层

怎么避免出错：
- 不要让接口直接返回 ORM 对象、`Map`、`JsonNode`
- 不要把临时字段当正式字段
- 不要让前端依赖“碰巧存在”的字段

### 2.2 先定分层，再搬代码

迁移不是“复制代码”，而是“重建边界”。

推荐顺序：
1. 定 DTO / BO / PO
2. 定 Repository 接口
3. 定 Infra 实现
4. 定 AppService 编排
5. 最后接 Controller 和前端

为什么：
- 先有边界，后有实现，代码不会乱串
- 后续替换数据源不会牵动整条链路

### 2.3 先定口径，再定展示

同一个指标可能有多个来源或多个算法口径。

必须先回答：
- 这是事实数据还是展示数据
- 是最新值还是历史值
- 是原始值还是修正值
- 是当前交易日还是上一个交易日

如果不先定，后面就会出现多个页面显示同一指标但数字不一致。

## 3. 常见坑的根因与预防

### 3.1 用动态对象顶接口

根因：
- 想快
- 不想一开始建很多类型

后果：
- 接口不可读
- 调用方无法编译期发现问题
- 改字段时容易漏

预防：
- 正式接口必须强类型
- 临时动态结构只允许存在于内部过渡层

### 3.2 把 SQL 放进 Java

根因：
- 看起来省事
- 方便调试

后果：
- 分层失效
- 查询逻辑散落
- 后续难做统一优化

预防：
- SQL 固定放 XML / Repository
- Java 只负责编排和转换

### 3.3 让前端自己拼口径

根因：
- 后端没把数据准备完整

后果：
- 每个前端组件都在猜
- 同一个页面多个组件口径不一致

预防：
- 前端只消费“已经算好的结果”
- 需要分组、排序、派生的字段尽量后端完成

### 3.4 只存结果，不存可追溯信息

根因：
- 只关心展示，不关心来源

后果：
- 数据错了以后很难追
- 没法知道是抓取错、计算错还是展示错

预防：
- 保留 source、tradeDate、updatedAt、raw/extra
- 派生数据和原始数据分开存

### 3.5 把“能解析”当成“已兼容”

根因：
- 解析成功几率高就觉得够了

后果：
- 遇到日期类型、枚举、未知字段时直接崩

预防：
- 明确 JSON 兼容策略
- 对 persisted JSON 设定稳定 DTO
- 对时间类型、未知字段、空数组做兜底

### 3.6 一个指标多种口径混用

根因：
- 历史遗留数据、实时数据、人工修正数据混在一起

后果：
- UI 表面能看，但数字不可信

预防：
- 统一建立“事实表 / 修正表 / 展示表”概念
- 每个接口明确读哪一层
- 同一页面不同区块如果口径不同，要显式说明

### 3.7 把 rawValue 当成 score

根因：
- 想让 UI 尽快显示数字
- 没有区分“原始指标”和“情绪得分”

后果：
- 页面看起来有数据，但口径错了
- 子卡和顶部综合指数可能显示不同含义的数字
- 后续策略、排序、颜色阈值都会被污染

预防：
- `score` 固定表示 0-100 的标准化得分
- `rawValue` 固定表示原始业务值，如收益差、成交额比率、创新高占比
- 前端可以同时展示 `score` 和 `rawValue`，但不能用 `rawValue` 冒充 `score`
- 如果 `score` 缺失，应回到 Java / 计算层补齐口径，不要让前端猜

### 3.8 顶部 composite 和子卡分项口径不一致

根因：
- 顶部综合指数已经有 components
- 子卡接口仍然只返回明细或原始值
- 单日接口和历史接口各自演进，字段不一致

后果：
- 顶部有分项分数，子卡却显示无数据
- 同一指标在同一页面出现两套解释
- sparkline 和主卡数字对不上

预防：
- 如果 composite 使用了某个 component score，子卡接口必须暴露同一个 score
- 单日接口和 history 接口都要补齐同一字段
- 子卡可以多返回 raw/source/detail，但主 score 要与 composite components 同口径
- 修复一个分项时同时检查 `/xxx`、`/xxx/history`、`/index` 或 composite 接口

### 3.9 字段别名只在前端兼容，没有回到契约层

根因：
- 后端返回 `date`，前端期望 `tradeDate`
- 临时在组件里写兼容逻辑

后果：
- 图表按日期对齐失败
- 兼容逻辑散落在多个组件里
- 后续新页面继续踩同一个坑

预防：
- Java DTO 明确输出稳定字段名，如 `tradeDate`
- 必要时保留旧字段做短期兼容，如同时返回 `date` 和 `tradeDate`
- 前端兼容别名应收敛在 `src/services/...`，组件只消费稳定模型
- 不要在组件里到处写 `it.date ?? it.tradeDate`

### 3.10 把 `0` 当成没数据

根因：
- 使用宽泛的 falsy 判断
- 没有定义 `null`、`0`、空数组的语义

后果：
- 有效的低分被隐藏
- 极端情绪状态显示成无数据

预防：
- `null` 表示未计算、缺失、不可用
- `0` 表示有效分数，只是最低值
- `[]` 表示查询成功但没有列表数据
- `ok=false` 表示业务失败或基础数据缺失
- 前端判断缺数据时使用 `value == null`，不要用 `!value`

### 3.11 只验证源码，没有验证运行中的服务

根因：
- 改了代码并编译通过后，默认认为页面已经使用新代码
- 本地仍然跑着旧 jar 或旧进程

后果：
- 请求仍然命中旧接口
- 代码和页面表现互相矛盾
- 排查时间被部署状态消耗

预防：
- 修改 Java 后确认当前运行进程对应的新 jar
- 重新 package 后停旧进程、启动本地新进程
- 验证真实端口 health
- 同时验证直连服务端口和 Gateway / Vite 代理结果

### 3.12 只修当前接口，漏掉历史接口

根因：
- 只盯着主卡显示
- 忽略 sparkline / 趋势图依赖 history

后果：
- 主数字有了，趋势图仍然空
- 单日和历史字段不一致
- UI 状态时好时坏

预防：
- 修一个指标时同时检查 snapshot 和 history
- history item 字段要和 snapshot 的核心字段保持一致
- 前端 service parser 要覆盖两类接口
- 验收时至少检查最新一条 history 是否和单日接口同日同口径

### 3.13 把动作型接口当成普通查询接口迁

根因：
- 只关注页面能不能点按钮
- 忽略动作执行后的状态、历史、失败原因和幂等语义

后果：
- Trigger 返回成功，但页面状态不更新
- 执行失败没有 run history，后面无法追溯
- Java、Python、数据库三边状态不一致

预防：
- 动作型接口必须定义请求 DTO、响应 DTO、状态回写和历史记录
- `trigger`、`enable`、`disable` 这类接口不能只返回 HTTP 成功
- 成功、失败、不支持、执行器不可达都要落到可查询状态
- UI 刷新依赖后端返回的业务状态，不要靠前端乐观猜测最终状态

### 3.14 没有建立旧任务 code 到新 job key 的映射

根因：
- 以为旧系统的 `job.code` 可以直接传给新执行器
- 没有把“调度元数据”和“真实执行能力”分开

后果：
- Java 调用 Python / 新执行器时出现 `unknown_job`
- 页面上看起来有任务，实际无法触发
- 旧任务名、展示名、执行器 job key 互相污染

预防：
- 为跨系统触发建立显式 resolver / mapping
- 旧 scheduler code 只代表业务调度身份
- 新执行器 job key 只代表可执行能力
- 无映射时返回明确失败，并写入状态和历史，而不是抛 500
- 后续可以在管理接口里暴露 `triggerSupported` / `executorJobKey`，让 UI 提前知道能否触发

### 3.15 只查列表，不验证分类、筛选、统计口径

根因：
- 列表接口返回数据后就认为页面完成
- 分类和统计只是前端状态，没有按真实业务重新校验

后果：
- 页面“按分类切换”没有反应
- 列表数量、分类数量、今日统计互相对不上
- UI 看起来有控件，但不是业务可用功能

预防：
- 列表、分类、统计、历史必须一起设计接口契约
- 分类切换要验证请求参数、返回结果和计数是否同步变化
- 如果分类是后端语义，过滤应由后端或 service 层统一处理
- 前端组件只管理交互状态，不重复实现业务分类规则

### 3.16 用通用 updateById 更新 JSONB / 复杂列

根因：
- 复用代码生成的通用更新方法
- 没有考虑 PostgreSQL `jsonb`、枚举、时间列的类型约束

后果：
- 简单字段更新带上 `jsonb` 列后失败
- enable / disable、状态回写这种小更新被复杂列拖垮
- 修复时容易绕回应用层拼 SQL

预防：
- 对 JSONB / 复杂列建立专用 XML 更新语句
- 小动作只更新必要列，不要整对象覆盖
- SQL 仍放 MyBatis XML，Java service 只调用明确语义的方法
- BasicService / Repository / DomainService 都要暴露同一业务语义的方法名

### 3.17 只验证执行器健康，不验证端到端触发链路

根因：
- 看到 Java health 或 Python health 正常，就认为 trigger 可用
- 没有从 Gateway、Java、执行器、数据库状态一起走一遍

后果：
- 执行器端口正常，但 Java 传错 job key
- Java trigger 正常返回，但状态表没更新
- 页面仍然看到旧状态

预防：
- 动作型接口至少验证四段：Gateway -> Java -> Executor -> DB
- 直连 Java 和经过 Gateway / Vite 代理都要测
- dry-run 触发后检查响应、job status、run history 三处
- 执行器未启动时也要返回可解释错误，并写入失败状态

### 3.18 把“不支持”当成异常，而不是业务状态

根因：
- 迁移期不支持的旧任务没有被建模
- 只考虑成功路径，失败路径临时抛异常

后果：
- 用户点旧任务直接 500
- UI 无法区分“暂未迁移”和“执行失败”
- 历史记录缺失，后续补迁没有依据

预防：
- 不支持的旧能力必须显式列出
- 如果数据库约束不允许 `unsupported`，可先用 `failed` 加明确 error message
- 响应 DTO 中保留 `ok`、`status`、`error`、`accepted` 等字段
- UI 根据业务状态展示失败原因，不把所有失败都当系统崩溃

### 3.19 前端 service 放错位置，页面后续不可维护

根因：
- 迁移时只想快速替换请求地址
- 把 Java API client 放进页面局部 `lib/api.ts`

后果：
- 不同页面重复封装同一类接口
- 后续 Java 接口调整时找不到调用点
- 页面组件承担了 service parser 和业务适配职责

预防：
- Java API client 按业务域放到 `src/services/...`
- 页面局部只保留视图状态和组合逻辑
- DTO 兼容、字段别名、空态归一化放在 service 层
- 迁移前先清理上一轮临时 API 文件，避免新旧入口并存

### 3.20 本地服务运行方式和验证环境不一致

根因：
- 本地、Docker、旧 jar、Vite proxy 混在一起
- 改完代码后没有确认页面实际命中哪一个服务

后果：
- 代码已经改了，页面仍然没变化
- 排查时误判为数据或前端问题
- 触发类接口可能打到旧进程，状态被写到预期之外的环境

预防：
- 按项目约定启动本地 Java / Vite / Python 服务
- 不用 Docker 启动 Cynexus 应用，除非任务明确要求
- 记录当前端口、进程、jar 时间和 health 结果
- 验证页面问题前先确认 Network 请求命中的是新接口

### 3.21 只迁主列表，漏掉点击后的二级入口

根因：
- 把页面理解成“一个 tab 对一个接口”
- 只跟踪首屏加载接口，没有把 drawer、dialog、钻入图、展开行、右键菜单等交互入口列出来
- 看到主列表有数据后就认为迁移完成

后果：
- 列表能显示，但点击 item 后 drawer / detail 为空
- 某个入口已经走 Java，另一个入口仍然走旧 Python
- 用户实际操作路径比验收路径更深，问题会在交互时才暴露

预防：
- 迁移前必须画出页面交互树，而不是只列接口清单
- 每个可点击区域都要追到最终数据源和 API client
- 验收时至少跑一遍：首屏 -> 点击 item -> drawer/dialog -> drill-down -> 子列表
- `rg` 检查页面目录和共享组件中是否仍有旧 `src/lib/api.ts`、旧 Python path、旧 endpoint 注释和旧 service import

### 3.22 只验证接口返回，不验证支撑表是否有数据

根因：
- 认为 Java endpoint 写好了就等于数据链路完成
- 没有检查 Java 查询依赖的 PG/CH 表是否已经导入或回填
- 没有区分“接口可用”和“支撑事实库有数据”

后果：
- API 返回 `ok=true`，但 `rows=[]`
- 前端看起来是渲染问题，实际是支撑表为空
- 后续刷新、回填、历史查询都没有可追溯来源

预防：
- 每个 Java 查询接口都要写出依赖表清单
- 接口验收前先查支撑表：行数、日期范围、自然键、必要外键/关联键
- 如果数据来自旧 reference / cache / DuckDB / parquet，必须明确导入脚本和导入结果
- 空表不是正常迁移结果，除非文档明确标记“暂无源数据”并且 UI 有对应空态

### 3.23 展示行缺少关联 key

根因：
- 只关注展示字段，如名称、涨跌幅、金额
- 忽略点击详情需要的业务 key，如 `industryCode`、`sectorCode`、`stockCode`、`targetKey`
- 旧系统可能通过 name -> code 的隐式映射补齐，新系统迁移时没有落库

后果：
- 列表行显示正常，但点击后无法查询详情
- 前端只能拿中文名称猜 code，容易错、不可维护
- 同名、简称、别名会导致详情查错或查空

预防：
- 列表 DTO 必须同时返回展示名和稳定业务 key
- 关联 key 应从后端 / 数据库补齐，不要让组件临时 name -> code
- 对所有可点击行检查：点击动作需要哪些 key，当前 DTO 是否都带齐
- 旧 reference 中的映射关系要迁入 PG 或 Java 稳定配置，不能只停留在旧文件里

### 3.24 共享组件仍然绑定旧 API

根因：
- 只改了页面主文件，忽略跨页面复用的 drawer、dialog、heatmap、table 组件
- 共享组件内部自己 import API client，调用方看不出来
- 迁移时没有做 import 级别的全局搜索

后果：
- 页面主接口已迁 Java，但共享组件继续请求 Python
- 不同入口同一个组件表现不一致
- 后续维护者以为页面已完成迁移，实际旧 API 还藏在组件内部

预防：
- 迁移页面时同时搜索 `views/<page>`、`components`、`services`、`lib/api.ts`
- 共享组件优先接收 data / loader prop；如果必须内置请求，API client 必须来自 `src/services/...`
- 不允许新迁移页面继续从全局 `src/lib/api.ts` 引入业务 API
- 删除或替换旧 import 后，跑 `rg "old endpoint|stock-chart|src/lib/api|Python API"` 确认没有残留

### 3.25 数据修复没有落成可重复脚本

根因：
- 为了快速修 UI，直接在数据库里手动 update / insert
- 没有把导入来源、字段映射、修复范围写下来

后果：
- 本机好了，其他环境无法复现
- 后续数据被清空或重建后，同样问题再次出现
- 不知道哪些数据来自旧 reference，哪些来自新采集链路

预防：
- 所有回填、映射修复、一次性导入都要落成脚本或 migration
- 脚本要支持 dry-run，输出导入行数、日期范围、关键计数
- 导入后把验证 SQL / endpoint smoke 结果写入 progress
- 数据库中的 `source`、`source_type`、`captured_at`、`extra` 要保留来源信息

## 4. 应该怎么设计，后面就不容易出问题

### 4.1 把数据分三层

- 原始层：事实、明细、可追溯
- 计算层：派生指标、聚合、分组、排名
- 展示层：UI 直接消费的轻量结果

不要把三层揉在一起。

### 4.2 把接口分两类

- 查询接口：只读、稳定、低副作用
- 执行接口：触发计算、刷新、回填、修复

不要让一个接口又查又写又修口径。

### 4.3 把兼容写进设计

兼容不是事后补丁，而是设计的一部分。

建议：
- DTO 保留字段别名
- 旧字段逐步废弃，不要一刀切
- 枚举和时间格式要固定
- 数组字段空时返回空数组，不要返回 `null`

### 4.4 把“缺数据”当成正常状态

很多页面不是没错误，而是有些区块天然会空。

建议：
- 每个接口都定义空态行为
- 不能拿到数据时返回明确的 `status`
- 前端不要依赖“字段一定存在”

### 4.5 指标接口统一返回三类字段

指标类接口建议明确区分三类字段：

- 标准分：`score`，0-100，用于主数字、颜色、排序、composite
- 原始值：`rawValue` 或更具体的业务字段，如 `spreadWeighted`、`ratio`、`pctNewHigh252d`
- 追溯信息：`tradeDate`、`source`、`fromCache`、`elapsedMs`、必要的 `extra`

如果历史原因已经存在更具体的 score 字段，例如 `sentimentScore`，可以短期保留，但应新增标准 `score` 别名，让前端和 Java 调用方有统一入口。

### 4.6 服务侧负责口径补齐，前端负责展示

当前端发现某个指标有 raw 但没有 score 时，不应该在组件里临时计算或猜测。

推荐顺序：
1. 查 composite / 汇总表是否已有同口径 score。
2. 如果已有，在 Java AppService 或 domain service 中按同交易日补齐。
3. 如果没有，回到计算层补齐持久化结果。
4. 前端只展示 `score`、`rawValue` 和明细解释，不承担核心指标口径。

### 4.7 把查询和动作分开设计

页面迁移不只包含查询 API，也可能包含动作 API。

查询 API 关注：
- 列表、详情、分类、统计、历史
- 分页、筛选、排序、空态
- 字段口径和展示契约

动作 API 关注：
- 请求参数、幂等键、dry-run
- 执行器映射、触发结果、错误归因
- 状态回写、历史记录、下一次轮询

不要用查询接口的验收标准去判断动作接口是否完成。动作接口必须证明“点了以后系统状态正确改变，失败时也能追溯”。

### 4.8 跨执行器调用要有适配层

Java 调 Python、Java 调采集器、Java 调其他内部服务时，不要把对方的内部命名直接暴露给页面或 scheduler 表。

推荐结构：
1. Controller 接收稳定 Java DTO。
2. AppService 根据业务对象做编排。
3. Resolver 把旧业务 code 映射成执行器 job key。
4. DomainService 调用 executor client。
5. Repository 写状态和历史。

这样旧 scheduler 元数据、新 executor 能力、UI 展示契约可以各自演进。

### 4.9 复杂列更新要设计专用写路径

存在 JSONB、数组、枚举、状态机字段时，不能默认使用整对象更新。

建议：
- 查询可以完整读取 PO / BO。
- 小动作更新使用 XML 中的专用 update。
- 状态回写只更新状态相关列。
- JSONB 只有在业务确实修改它时才写。
- 每个专用 update 都对应一个 BasicService / Repository 语义方法。

### 4.10 把页面迁移拆成“入口契约”和“支撑数据契约”

一个页面迁移至少有两张表要维护：

- 入口契约：页面会调用哪些 API，哪些组件会触发二级请求
- 支撑数据契约：每个 API 依赖哪些 PG/CH 表、哪些 reference/cache、哪些关联 key

推荐在迁移前写成表格：

| UI 入口 | Java API | 前端 service | 依赖表/数据源 | 关联 key | 验收 |
|---|---|---|---|---|---|
| 主列表 | `/api/...` | `src/services/...` | `table_a` | `id/code` | 行数/日期/API |
| 点击行 drawer | `/api/.../{code}` | `src/services/...` | `table_b` | `code` | rows 非空 |
| 图表 drill-down | `/api/.../{code}/detail` | `src/services/...` | `table_c` | `code` | 点击后非空 |

只有主入口和二级入口都通过，页面迁移才算完成。

## 5. 迁移前检查清单

1. 这个页面的接口契约有没有先定下来。
2. 每个字段的来源是什么，能不能追溯。
3. 哪些字段是原始值，哪些是计算值。
4. 是否存在多个来源口径冲突。
5. 是否需要历史、最新、上一交易日三种视角。
6. 是否有空数组、空对象、null 的统一策略。
7. 是否有时间字段、枚举字段、JSONB 字段的兼容处理。
8. 是否把 SQL 留在仓储层。
9. 是否避免了 `Map`、`JsonNode` 这类长期接口结构。
10. 是否把前端需要展开、筛选、排序的字段都提前准备好。
11. 指标类接口是否明确区分 `score` 和 `rawValue`。
12. composite components 和子卡分项 score 是否同口径。
13. 单日接口和 history 接口是否返回同一套核心字段。
14. `0`、`null`、`[]`、`ok=false` 的语义是否明确。
15. 前端兼容字段别名是否收敛在 service 层，而不是散落在组件里。
16. 动作型接口是否定义了状态回写和历史记录。
17. 旧 code 与新 executor job key 是否有显式映射。
18. 不支持的旧能力是否有明确失败响应，而不是 500。
19. 分类、筛选、统计是否一起验收，而不是只看列表。
20. JSONB / 复杂列是否避免了通用整对象更新。
21. 前端 API client 是否放在 `src/services/...` 的业务目录下。
22. 当前页面是否确认命中了本地最新 Java 服务，而不是旧进程或 Docker。
23. 页面所有点击入口、drawer、dialog、drill-down、展开行是否都列入接口清单。
24. 共享组件内部是否仍然 import 旧 API client。
25. 每个可点击行是否返回后续查询需要的稳定 key。
26. Java 查询依赖的支撑表是否已经有数据，行数和日期范围是否正确。
27. 旧 reference/cache/DuckDB/parquet 数据是否已有可重复导入脚本。
28. 是否用 `rg` 搜索确认旧 Python endpoint / `src/lib/api.ts` 调用没有残留在 scope 内。

## 6. 迁移完成后的验收标准

- 接口字段是显式 DTO，不靠猜。
- SQL 没有散进应用层。
- 每个指标有明确来源和口径。
- 前端不需要自己补算核心业务逻辑。
- 空态、异常态、历史态都有明确表现。
- 本地直连和 Gateway 转发结果一致。
- 指标 score 由 Java / 计算层提供，前端没有用 rawValue 冒充 score。
- 单日接口和 history 接口最新一条数据同日同口径。
- `score=0` 能正常显示，不会被当成无数据。
- 实际运行进程已经重启到最新 jar，页面请求命中新接口。
- 动作接口触发后，响应、状态表、历史表三者一致。
- 不支持的任务有明确业务失败原因，页面不会崩。
- 分类切换、筛选、统计和列表数据联动正确。
- JSONB / 复杂列的小更新走专用仓储方法和 MyBatis XML。
- 所有二级交互入口都命中 Java service，并且返回非空或明确空态。
- 展示列表携带后续详情查询需要的稳定 key。
- 支撑表的数据量、日期范围、source/source_type 已经记录。
- 一次性数据修复有脚本或 migration 可重复执行。

## 7. 运行验证流程

迁移完成后，不要只看源码和编译结果。建议固定执行：

1. Java 编译或打包通过。
2. 停掉旧本地服务进程。
3. 启动新 jar。
4. 检查服务端口和 health。
5. 直连 Java 服务验证核心接口。
6. 通过 Gateway / Vite 代理再验证同一接口。
7. 对比 payload 关键字段，包括 `tradeDate`、`score`、`rawValue`、history 最新一条。
8. 点击页面上的列表行、图表块、drawer/dialog、drill-down，确认二级接口也命中新服务。
9. 查询支撑表行数、日期范围、必要关联 key 非空率。
10. 最后打开页面确认 UI 使用的是同一份数据。

动作型页面额外执行：

1. 验证分类 / 筛选切换能改变请求参数和返回数据。
2. 触发一个支持的 dry-run job，检查响应 `ok=true`。
3. 触发一个不支持或故意失败的 job，检查响应有明确 error。
4. 查询列表确认 `lastStatus` / `lastRunAt` 更新。
5. 查询 history 确认成功和失败都留下记录。
6. 检查服务日志中没有 JSONB 类型错误、执行器 `unknown_job`、旧端口请求。

数据回填 / 导入型页面额外执行：

1. 运行导入脚本 `--dry-run`，确认源文件数量、日期范围、预计行数。
2. 执行导入后查询目标表行数、distinct key、min/max date。
3. 查询主列表接口，确认关联 key 已补齐。
4. 查询二级详情接口，确认 rows 非空或空态合理。
5. 记录导入脚本路径、源数据路径和验证结果。

## 8. 一句话总结

迁移的目标不是把 Python 变成 Java，
而是把“临时可用”变成“长期可维护”。
