# Python -> Java API 迁移通用 Guide

这是一份面向后续所有页面迁移的通用指南，不绑定某个具体页面。
目标不是“把代码搬过去”，而是“把数据契约、分层边界、口径一致性和可维护性一起迁过去”。

## 1. 先理解问题为什么会发生

### 1.1 迁移时最容易犯的错

很多迁移失败，不是实现能力不够，而是默认把“能跑”当成了“迁移完成”。

常见误区：
- 先把接口跑起来，再回头补契约
- 先让前端显示出来，再回头补数据口径
- 先用 `Map` / `JsonNode` 顶住，再说后面重构
- 先把 SQL 写进去，再说后面分层

这些做法短期有效，长期会把系统带进“能用但不可维护”的状态。

### 1.2 问题的根因

迁移时真正难的不是代码量，而是四类边界：
- 数据边界：原始数据、派生数据、展示数据是否分清
- 责任边界：谁负责采集，谁负责计算，谁负责服务
- 契约边界：接口字段是否稳定、可读、可追溯
- 口径边界：同一指标是否所有入口都取同一种定义

只要这些边界不先定，后面一定会出现“看起来对了，实际上错了”的情况。

## 2. 迁移的核心原则

### 2.1 先定契约，再写实现

先定义 DTO / Request / Response，再写服务逻辑。

为什么：
- 契约先行会逼你想清楚字段来源
- 前后端可以并行推进
- 后期改动只会影响少量边界层

怎么避免出错：
- 不要让接口直接返回 ORM 对象、`Map`、`JsonNode`
- 不要把临时字段当正式字段
- 不要让前端依赖“碰巧存在”的字段

### 2.2 先定分层，再搬代码

迁移不是“复制代码”，而是“重建边界”。

推荐顺序：
1. 定 DTO / BO / PO
2. 定 Repository 接口
3. 定 Infra 实现
4. 定 AppService 编排
5. 最后接 Controller 和前端

为什么：
- 先有边界，后有实现，代码不会乱串
- 后续替换数据源不会牵动整条链路

### 2.3 先定口径，再定展示

同一个指标可能有多个来源或多个算法口径。

必须先回答：
- 这是事实数据还是展示数据
- 是最新值还是历史值
- 是原始值还是修正值
- 是当前交易日还是上一个交易日

如果不先定，后面就会出现多个页面显示同一指标但数字不一致。

## 3. 常见坑的根因与预防

### 3.1 用动态对象顶接口

根因：
- 想快
- 不想一开始建很多类型

后果：
- 接口不可读
- 调用方无法编译期发现问题
- 改字段时容易漏

预防：
- 正式接口必须强类型
- 临时动态结构只允许存在于内部过渡层

### 3.2 把 SQL 放进 Java

根因：
- 看起来省事
- 方便调试

后果：
- 分层失效
- 查询逻辑散落
- 后续难做统一优化

预防：
- SQL 固定放 XML / Repository
- Java 只负责编排和转换

### 3.3 让前端自己拼口径

根因：
- 后端没把数据准备完整

后果：
- 每个前端组件都在猜
- 同一个页面多个组件口径不一致

预防：
- 前端只消费“已经算好的结果”
- 需要分组、排序、派生的字段尽量后端完成

### 3.4 只存结果，不存可追溯信息

根因：
- 只关心展示，不关心来源

后果：
- 数据错了以后很难追
- 没法知道是抓取错、计算错还是展示错

预防：
- 保留 source、tradeDate、updatedAt、raw/extra
- 派生数据和原始数据分开存

### 3.5 把“能解析”当成“已兼容”

根因：
- 解析成功几率高就觉得够了

后果：
- 遇到日期类型、枚举、未知字段时直接崩

预防：
- 明确 JSON 兼容策略
- 对 persisted JSON 设定稳定 DTO
- 对时间类型、未知字段、空数组做兜底

### 3.6 一个指标多种口径混用

根因：
- 历史遗留数据、实时数据、人工修正数据混在一起

后果：
- UI 表面能看，但数字不可信

预防：
- 统一建立“事实表 / 修正表 / 展示表”概念
- 每个接口明确读哪一层
- 同一页面不同区块如果口径不同，要显式说明

### 3.7 把 rawValue 当成 score

根因：
- 想让 UI 尽快显示数字
- 没有区分“原始指标”和“情绪得分”

后果：
- 页面看起来有数据，但口径错了
- 子卡和顶部综合指数可能显示不同含义的数字
- 后续策略、排序、颜色阈值都会被污染

预防：
- `score` 固定表示 0-100 的标准化得分
- `rawValue` 固定表示原始业务值，如收益差、成交额比率、创新高占比
- 前端可以同时展示 `score` 和 `rawValue`，但不能用 `rawValue` 冒充 `score`
- 如果 `score` 缺失，应回到 Java / 计算层补齐口径，不要让前端猜

### 3.8 顶部 composite 和子卡分项口径不一致

根因：
- 顶部综合指数已经有 components
- 子卡接口仍然只返回明细或原始值
- 单日接口和历史接口各自演进，字段不一致

后果：
- 顶部有分项分数，子卡却显示无数据
- 同一指标在同一页面出现两套解释
- sparkline 和主卡数字对不上

预防：
- 如果 composite 使用了某个 component score，子卡接口必须暴露同一个 score
- 单日接口和 history 接口都要补齐同一字段
- 子卡可以多返回 raw/source/detail，但主 score 要与 composite components 同口径
- 修复一个分项时同时检查 `/xxx`、`/xxx/history`、`/index` 或 composite 接口

### 3.9 字段别名只在前端兼容，没有回到契约层

根因：
- 后端返回 `date`，前端期望 `tradeDate`
- 临时在组件里写兼容逻辑

后果：
- 图表按日期对齐失败
- 兼容逻辑散落在多个组件里
- 后续新页面继续踩同一个坑

预防：
- Java DTO 明确输出稳定字段名，如 `tradeDate`
- 必要时保留旧字段做短期兼容，如同时返回 `date` 和 `tradeDate`
- 前端兼容别名应收敛在 `src/services/...`，组件只消费稳定模型
- 不要在组件里到处写 `it.date ?? it.tradeDate`

### 3.10 把 `0` 当成没数据

根因：
- 使用宽泛的 falsy 判断
- 没有定义 `null`、`0`、空数组的语义

后果：
- 有效的低分被隐藏
- 极端情绪状态显示成无数据

预防：
- `null` 表示未计算、缺失、不可用
- `0` 表示有效分数，只是最低值
- `[]` 表示查询成功但没有列表数据
- `ok=false` 表示业务失败或基础数据缺失
- 前端判断缺数据时使用 `value == null`，不要用 `!value`

### 3.11 只验证源码，没有验证运行中的服务

根因：
- 改了代码并编译通过后，默认认为页面已经使用新代码
- 本地仍然跑着旧 jar 或旧进程

后果：
- 请求仍然命中旧接口
- 代码和页面表现互相矛盾
- 排查时间被部署状态消耗

预防：
- 修改 Java 后确认当前运行进程对应的新 jar
- 重新 package 后停旧进程、启动本地新进程
- 验证真实端口 health
- 同时验证直连服务端口和 Gateway / Vite 代理结果

### 3.12 只修当前接口，漏掉历史接口

根因：
- 只盯着主卡显示
- 忽略 sparkline / 趋势图依赖 history

后果：
- 主数字有了，趋势图仍然空
- 单日和历史字段不一致
- UI 状态时好时坏

预防：
- 修一个指标时同时检查 snapshot 和 history
- history item 字段要和 snapshot 的核心字段保持一致
- 前端 service parser 要覆盖两类接口
- 验收时至少检查最新一条 history 是否和单日接口同日同口径

## 4. 应该怎么设计，后面就不容易出问题

### 4.1 把数据分三层

- 原始层：事实、明细、可追溯
- 计算层：派生指标、聚合、分组、排名
- 展示层：UI 直接消费的轻量结果

不要把三层揉在一起。

### 4.2 把接口分两类

- 查询接口：只读、稳定、低副作用
- 执行接口：触发计算、刷新、回填、修复

不要让一个接口又查又写又修口径。

### 4.3 把兼容写进设计

兼容不是事后补丁，而是设计的一部分。

建议：
- DTO 保留字段别名
- 旧字段逐步废弃，不要一刀切
- 枚举和时间格式要固定
- 数组字段空时返回空数组，不要返回 `null`

### 4.4 把“缺数据”当成正常状态

很多页面不是没错误，而是有些区块天然会空。

建议：
- 每个接口都定义空态行为
- 不能拿到数据时返回明确的 `status`
- 前端不要依赖“字段一定存在”

### 4.5 指标接口统一返回三类字段

指标类接口建议明确区分三类字段：

- 标准分：`score`，0-100，用于主数字、颜色、排序、composite
- 原始值：`rawValue` 或更具体的业务字段，如 `spreadWeighted`、`ratio`、`pctNewHigh252d`
- 追溯信息：`tradeDate`、`source`、`fromCache`、`elapsedMs`、必要的 `extra`

如果历史原因已经存在更具体的 score 字段，例如 `sentimentScore`，可以短期保留，但应新增标准 `score` 别名，让前端和 Java 调用方有统一入口。

### 4.6 服务侧负责口径补齐，前端负责展示

当前端发现某个指标有 raw 但没有 score 时，不应该在组件里临时计算或猜测。

推荐顺序：
1. 查 composite / 汇总表是否已有同口径 score。
2. 如果已有，在 Java AppService 或 domain service 中按同交易日补齐。
3. 如果没有，回到计算层补齐持久化结果。
4. 前端只展示 `score`、`rawValue` 和明细解释，不承担核心指标口径。

## 5. 迁移前检查清单

1. 这个页面的接口契约有没有先定下来。
2. 每个字段的来源是什么，能不能追溯。
3. 哪些字段是原始值，哪些是计算值。
4. 是否存在多个来源口径冲突。
5. 是否需要历史、最新、上一交易日三种视角。
6. 是否有空数组、空对象、null 的统一策略。
7. 是否有时间字段、枚举字段、JSONB 字段的兼容处理。
8. 是否把 SQL 留在仓储层。
9. 是否避免了 `Map`、`JsonNode` 这类长期接口结构。
10. 是否把前端需要展开、筛选、排序的字段都提前准备好。
11. 指标类接口是否明确区分 `score` 和 `rawValue`。
12. composite components 和子卡分项 score 是否同口径。
13. 单日接口和 history 接口是否返回同一套核心字段。
14. `0`、`null`、`[]`、`ok=false` 的语义是否明确。
15. 前端兼容字段别名是否收敛在 service 层，而不是散落在组件里。

## 6. 迁移完成后的验收标准

- 接口字段是显式 DTO，不靠猜。
- SQL 没有散进应用层。
- 每个指标有明确来源和口径。
- 前端不需要自己补算核心业务逻辑。
- 空态、异常态、历史态都有明确表现。
- 本地直连和 Gateway 转发结果一致。
- 指标 score 由 Java / 计算层提供，前端没有用 rawValue 冒充 score。
- 单日接口和 history 接口最新一条数据同日同口径。
- `score=0` 能正常显示，不会被当成无数据。
- 实际运行进程已经重启到最新 jar，页面请求命中新接口。

## 7. 运行验证流程

迁移完成后，不要只看源码和编译结果。建议固定执行：

1. Java 编译或打包通过。
2. 停掉旧本地服务进程。
3. 启动新 jar。
4. 检查服务端口和 health。
5. 直连 Java 服务验证核心接口。
6. 通过 Gateway / Vite 代理再验证同一接口。
7. 对比 payload 关键字段，包括 `tradeDate`、`score`、`rawValue`、history 最新一条。
8. 最后打开页面确认 UI 使用的是同一份数据。

## 8. 一句话总结

迁移的目标不是把 Python 变成 Java，
而是把“临时可用”变成“长期可维护”。
