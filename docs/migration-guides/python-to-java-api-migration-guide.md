# Python -> Java API 迁移通用 Guide

这是一份面向后续所有页面迁移的通用指南，不绑定某个具体页面。
目标不是“把代码搬过去”，而是“把数据契约、分层边界、口径一致性和可维护性一起迁过去”。

## 1. 先理解问题为什么会发生

### 1.1 迁移时最容易犯的错

很多迁移失败，不是实现能力不够，而是默认把“能跑”当成了“迁移完成”。

常见误区：
- 先把接口跑起来，再回头补契约
- 先让前端显示出来，再回头补数据口径
- 先用 `Map` / `JsonNode` 顶住，再说后面重构
- 先把 SQL 写进去，再说后面分层

这些做法短期有效，长期会把系统带进“能用但不可维护”的状态。

### 1.2 问题的根因

迁移时真正难的不是代码量，而是四类边界：
- 数据边界：原始数据、派生数据、展示数据是否分清
- 责任边界：谁负责采集，谁负责计算，谁负责服务
- 契约边界：接口字段是否稳定、可读、可追溯
- 口径边界：同一指标是否所有入口都取同一种定义

只要这些边界不先定，后面一定会出现“看起来对了，实际上错了”的情况。

## 2. 迁移的核心原则

### 2.1 先定契约，再写实现

先定义 DTO / Request / Response，再写服务逻辑。

为什么：
- 契约先行会逼你想清楚字段来源
- 前后端可以并行推进
- 后期改动只会影响少量边界层

怎么避免出错：
- 不要让接口直接返回 ORM 对象、`Map`、`JsonNode`
- 不要把临时字段当正式字段
- 不要让前端依赖“碰巧存在”的字段

### 2.2 先定分层，再搬代码

迁移不是“复制代码”，而是“重建边界”。

推荐顺序：
1. 定 DTO / BO / PO
2. 定 Repository 接口
3. 定 Infra 实现
4. 定 AppService 编排
5. 最后接 Controller 和前端

为什么：
- 先有边界，后有实现，代码不会乱串
- 后续替换数据源不会牵动整条链路

### 2.3 先定口径，再定展示

同一个指标可能有多个来源或多个算法口径。

必须先回答：
- 这是事实数据还是展示数据
- 是最新值还是历史值
- 是原始值还是修正值
- 是当前交易日还是上一个交易日

如果不先定，后面就会出现多个页面显示同一指标但数字不一致。

## 3. 常见坑的根因与预防

### 3.1 用动态对象顶接口

根因：
- 想快
- 不想一开始建很多类型

后果：
- 接口不可读
- 调用方无法编译期发现问题
- 改字段时容易漏

预防：
- 正式接口必须强类型
- 临时动态结构只允许存在于内部过渡层

### 3.2 把 SQL 放进 Java

根因：
- 看起来省事
- 方便调试

后果：
- 分层失效
- 查询逻辑散落
- 后续难做统一优化

预防：
- SQL 固定放 XML / Repository
- Java 只负责编排和转换

### 3.3 让前端自己拼口径

根因：
- 后端没把数据准备完整

后果：
- 每个前端组件都在猜
- 同一个页面多个组件口径不一致

预防：
- 前端只消费“已经算好的结果”
- 需要分组、排序、派生的字段尽量后端完成

### 3.4 只存结果，不存可追溯信息

根因：
- 只关心展示，不关心来源

后果：
- 数据错了以后很难追
- 没法知道是抓取错、计算错还是展示错

预防：
- 保留 source、tradeDate、updatedAt、raw/extra
- 派生数据和原始数据分开存

### 3.5 把“能解析”当成“已兼容”

根因：
- 解析成功几率高就觉得够了

后果：
- 遇到日期类型、枚举、未知字段时直接崩

预防：
- 明确 JSON 兼容策略
- 对 persisted JSON 设定稳定 DTO
- 对时间类型、未知字段、空数组做兜底

### 3.6 一个指标多种口径混用

根因：
- 历史遗留数据、实时数据、人工修正数据混在一起

后果：
- UI 表面能看，但数字不可信

预防：
- 统一建立“事实表 / 修正表 / 展示表”概念
- 每个接口明确读哪一层
- 同一页面不同区块如果口径不同，要显式说明

## 4. 应该怎么设计，后面就不容易出问题

### 4.1 把数据分三层

- 原始层：事实、明细、可追溯
- 计算层：派生指标、聚合、分组、排名
- 展示层：UI 直接消费的轻量结果

不要把三层揉在一起。

### 4.2 把接口分两类

- 查询接口：只读、稳定、低副作用
- 执行接口：触发计算、刷新、回填、修复

不要让一个接口又查又写又修口径。

### 4.3 把兼容写进设计

兼容不是事后补丁，而是设计的一部分。

建议：
- DTO 保留字段别名
- 旧字段逐步废弃，不要一刀切
- 枚举和时间格式要固定
- 数组字段空时返回空数组，不要返回 `null`

### 4.4 把“缺数据”当成正常状态

很多页面不是没错误，而是有些区块天然会空。

建议：
- 每个接口都定义空态行为
- 不能拿到数据时返回明确的 `status`
- 前端不要依赖“字段一定存在”

## 5. 迁移前检查清单

1. 这个页面的接口契约有没有先定下来。
2. 每个字段的来源是什么，能不能追溯。
3. 哪些字段是原始值，哪些是计算值。
4. 是否存在多个来源口径冲突。
5. 是否需要历史、最新、上一交易日三种视角。
6. 是否有空数组、空对象、null 的统一策略。
7. 是否有时间字段、枚举字段、JSONB 字段的兼容处理。
8. 是否把 SQL 留在仓储层。
9. 是否避免了 `Map`、`JsonNode` 这类长期接口结构。
10. 是否把前端需要展开、筛选、排序的字段都提前准备好。

## 6. 迁移完成后的验收标准

- 接口字段是显式 DTO，不靠猜。
- SQL 没有散进应用层。
- 每个指标有明确来源和口径。
- 前端不需要自己补算核心业务逻辑。
- 空态、异常态、历史态都有明确表现。
- 本地直连和 Gateway 转发结果一致。

## 7. 一句话总结

迁移的目标不是把 Python 变成 Java，
而是把“临时可用”变成“长期可维护”。
