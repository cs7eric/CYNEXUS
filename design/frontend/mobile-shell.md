# Mobile Shell

The mobile experience lives in the same React application but has its own route tree and shell. The current routes are `/m`, `/m/apps`, `/m/finance`, `/m/workout`, and `/m/me`; other business pages remain desktop links until they are migrated.

The user's preferred visual direction and original reference set are recorded in [Mobile visual direction](mobile-visual-direction.md). Use that reference for future mobile visual work; this document describes the currently implemented shell.

## Boundaries

- `src/mobile/layout/` owns the mobile header, tab bar, scroll container, safe-area handling, and overlay portal.
- `src/mobile/pages/<app>/` owns each mobile route as a dedicated page folder; `index.tsx` is the route entry and page-only styles stay beside it.
- `src/mobile/components/` contains mobile compositions that link to desktop pages during migration.
- `src/mobile/ui/` is the thin project wrapper around HeroUI components. Use HeroUI only inside the mobile tree.
- `src/services/`, authentication, APIs, and business validation remain shared.

## Header

All mobile routes share a floating header: an 80px row with a centered greeting and current English date, a 44px leading control, and app search on the right. The header is transparent at the top; after scrolling more than 8px, a uniform 28%-opaque white layer with 6px backdrop blur fades in behind its controls and safe area. Returning to the top restores transparency. Browsers without backdrop filtering use a uniform 44%-opaque white fallback. The shared scroll-restoration hook keeps the effect consistent across route/workspace changes and restored scroll positions. In the Home area (`/m`, `/m/apps`, `/m/me`), the leading icon opens the workspace switcher. Inside an app route, it becomes a back arrow that returns to `/m`. Finance also places its refresh action beside the leading control. Page content scrolls underneath it; the initial content offset keeps its controls clear. Each page identifies its own content in the scrolling region. Profile provides the desktop-version link, and the not-found page provides Back to Home.

The workspace switcher opens an anchored 264px white popover with 28px corners and 60px rounded options. Circular icons, a pale-blue selected surface and a dark check indicator identify the active workspace; the trigger gets a subtle expanded-state ring. It retains the HeroUI menu's radio semantics, keyboard navigation, focus restoration and outside/Escape dismissal. The popover stays within narrow viewports and the mobile overlay portal.

Search uses a native modal dialog with keyboard focus, Escape dismissal, filtering of actual workspace apps and real destination links. Its styles and the locally hosted Manrope font load with the mobile layout, including direct visits to Apps and Profile before Home has loaded.

Mobile interface copy is English, including Home, Apps and Profile titles, navigation, workspace names, help text, tooltips, accessibility labels, authentication and confirmation dialogs. The mobile language attribute is `en`, and its React Aria locale provider uses `en-US` so component labels also remain English in non-English browsers. User content and business data retain their original language.

The desktop shell keeps using shadcn/Radix primitives. HeroUI styles are imported by `src/mobile/styles.css` and prefixed below `.mobile-theme`; this prevents component selectors and theme variables from changing desktop pages. Overlay components use the mobile portal so their visual scope remains inside the mobile theme.

## Bottom navigation

The Home area (`/m`, `/m/apps`, `/m/me`) uses the global Home, Apps, Finance, Workout and Profile tabs. Finance and Workout routes replace them with that app's own configured tabs. Finance tabs switch between Overview, Accounts and Activity views; Workout tabs switch between Overview, Activity, Body and History views. Both navigation modes use the same detached frosted-white capsule, mist-blue active pill, circular `+` button and quick-action menu. The capsule and `+` are both 64px tall at every viewport width. Their surfaces share a subtle white border and soft shadow, with 72%-opaque white and 12px backdrop blur (94%-opaque white when blur is unavailable). Inactive icons and labels use muted blue-gray; the active pill uses dark blue text. The `+` retains its dark inset circle and vertical quick-action expansion. The bar has 20px side spacing (16px below 360px), a 440px maximum width and bottom spacing equal to the larger of 12px or the device safe-area inset. Each tab stacks its 20px outline icon above its 10px, weight-600 English label (18px icons and 9px labels below 360px). Active colors transition smoothly; `aria-current` and visible keyboard focus identify the current and focused destinations.

The header and tab bar persist outside the route outlet in the full-height mobile shell. The header remains above the scrolling content; the tab bar is an absolute transparent overlay anchored to the shell bottom. Its outer area passes pointer events through and has no painted background; only the white capsule and pale-blue active pill are visible. The route container and scroll padding reserve clearance so the final content and focused controls remain reachable without being covered. Shared neutral colors, typography, search and navigation styles belong to `src/mobile/styles.css`; Home's colored cards and artwork remain in its page CSS. The shared content column is capped at 440px.

The mobile theme inherits the existing `html` / `body` / `#root` height chain. Ordinary Safari uses the small viewport (`100svh`), leaving Safari's top and bottom browser controls outside the app; an installed Home Screen app switches to the dynamic visual viewport and can use the full screen. The viewport allows device safe areas and content resizing when a supported browser opens the keyboard. Home-screen metadata uses the light interface's default status-bar treatment. Header, navigation and content retain safe-area insets. The transparent header overlays the scroll region while its top content offset prevents the first item from starting underneath its controls. Desktop height rules remain unchanged. A website cannot hide Safari's browser controls; standalone mode provides the app-like presentation. Browser viewport emulation does not verify an installed iOS home-screen app; device-specific viewport workarounds require evidence from that environment.

## Routing and state

Mobile routes are lazy loaded under `/m`. The route is explicit while the scaffold is being validated; automatic device-based redirects should wait until real mobile business workflows exist. The mobile shell can open the last desktop page for the active workspace. Mobile navigation does not overwrite those desktop destinations.

The personal/development workspace model is shared, but mobile workspace switching keeps the user on the current mobile route. A mobile page should preserve back behavior, scroll position, safe-area insets, keyboard-friendly controls, and a clear desktop fallback while its business page is not migrated.

## Activity calendar preview

Home's static week strip is replaced by `src/mobile/components/activity-calendar/`. The default is the selected date's Sunday–Saturday week. Month expands inline to the selected date's calendar month, aligned to whole weeks. Swipe left for the next month or right for the previous month; labeled arrow buttons provide the same navigation. Vertical scrolling, pinch zoom and ordinary date taps remain available; short, vertical and cancelled gestures do not change months, and a horizontal swipe does not select a date. A stable six-row area prevents the summary from jumping between months. Padding dates and future dates are disabled; historical dates are selectable even beyond the 30-day sample fixture. Browsing months preserves the selected date and its details. Selecting a day updates its food intake in kcal, meal count, workout duration in minutes and activity label. Collapsing keeps the selected day and its week; Today restores both the current month and date. Arrow keys can cross month boundaries, Home/End, a single available date tab stop, date/selection semantics and polite month/detail announcements support keyboard and screen-reader use.

Weekday labels sit in a separate aligned row above the compact 96px white capsules. Each capsule contains a clear date numeral and two centered food/workout rows with small icons; an 8px date-to-metric gap and 6px metric gap leave breathing room without lengthening the capsule. Missing values are muted, rest days remain explicit, and the selected date uses the shell's near-black surface with sky/mint values. The expanded calendar retains its compact date grid.

This is the user-requested visual prototype. Home passes explicitly labeled `Sample data` from a separate fixture module. `DailyActivity` accepts independent nullable nutrition/workout records: missing logs show an em dash and explanatory text; a recorded rest day shows zero minutes and `Rest day`. Daily nutrition targets are explicit sample values, separate from intake logs and stored per date so historical targets can differ. No target calculation, health advice, completion scores, persistence or backend calls are added. Autonomous Agent exposure is excluded at this stage because this preview provides no foundational real-data read or write operation. A future real-data integration must replace the fixtures and evaluate safe Agent access separately.

The selected day's Today/date details use a cool-blue Food intake card beside a mint Workout card. Food intake is slightly wider and contains consumed / target kcal, meal count and three compact `Carbs`, `Protein`, `Fat` rows. Small wheat, protein and droplet icons plus blue, mint and slate 3px intake bars distinguish the rows without separate tiles or a nutrition section. Each row shows consumed grams / daily target, with stronger type for intake. Workout shows duration, activity and logged sessions, retaining its own meaning. Bars cap at the goal while text preserves values above it; a missing intake or non-positive/missing goal leaves an empty track without implying a loading state. Values use grams with up to one decimal place and update with the selected date in either calendar view. Intake and targets are independently nullable: missing intake shows an em dash with `Not logged` assistive text, and missing goals show an em dash with `daily target not set`; available values remain visible. Macro values and goals belong only to daily details and are supplied explicitly by the labeled sample fixtures, rather than inferred from calories. The current sample goals are 2,200 kcal, 250 g carbs, 120 g protein and 80 g fat.

Date helpers use local calendar arithmetic at noon, avoiding UTC date parsing and 24-hour millisecond increments across DST boundaries. Focused tests cover full calendar months, month shifts from the 29th–31st, leap days, year boundaries, partial weeks, unavailable future days and DST timezones. Colors and rounded shapes extend the approved Home/Profile palette; the shared header, tabs and page scrolling remain stable.

## Apps

`/m/apps` is implemented in `src/mobile/pages/apps/index.tsx` with `apps.css` beside it. It matches Home and Profile: a compact 20px title, current workspace and actual app count, then sky-blue/mint rounded shortcuts for the two shared apps. Workspace-specific groups are unboxed 68px rows with 23px outline icons, 15px labels, thin dividers and chevrons, using the same spacing and neutral palette as Profile. The old framed white cards and green icon tiles are no longer used by the directory.

All groups, app names, counts and destinations come from the existing navigation configuration. Switching workspace in the shared header updates the directory in place; each app link carries the current workspace to the desktop destination. The fixed greeting header and capsule navigation stay visible while the list scrolls. No usage metrics or new business functionality are implied.

## Profile

The fourth tab is Profile at the existing `/m/me` address, implemented in `src/mobile/pages/profile/index.tsx` with page-local CSS. It adapts the supplied fitness profile into Cynexus: configured username/email and an initials avatar, current workspace and owner access, then mint/sky/slate summaries with the actual Personal, Development and shared app counts from navigation configuration. These app counts describe available navigation entries, not usage or backend health. Summary links open the matching app directory and retain the selected workspace.

## Finance

The third tab opens `/m/finance`, implemented in `src/mobile/pages/finance/index.tsx`. Overview is the default view and renders current CNY asset balances as an overlapping pile of the supplied single-note and coin cutouts. Its exact amount, net assets and liabilities come from signed, unarchived CNY account balances in the shared overview service. Other or unspecified currencies are excluded with a visible note; no exchange rate is assumed. Missing or unsafe balances make the corresponding total unavailable. Zero and negative assets show their exact value without a positive money pile.

The pile decomposes integer fen into decimal groups of at least ¥1,000 and individual denominations down to ¥0.01. Bundles represent ¥100 notes, with a tilted top face, visible layered paper edges and a wrapping band that continues down the stack. Thousand-yuan bundles are thinner than ten-thousand-yuan bundles; higher groups use bounded thickness. Bundles sit above loose notes so their thickness remains visible. Every bundle of ¥10k or more is placed separately with its own denomination band: ¥50,000 shows five ¥10k bundles, with no combined badge. Repeated ¥1k bundles, loose notes or coins above four retain a shared visual with a quantity badge. Decimal grouping keeps the number of bundles bounded even for large balances. A caption and the native “Inside your pile” modal expose the exact composition. Placement is deterministic, money images are decorative to assistive technology, and reduced-motion preferences are respected. Overview has a local refresh action, explicit loading/error/stale states, and a privacy toggle that removes amounts, composition and pile imagery from the rendered page. This is a visualization of the existing read capability, already covered by the `finance.overview` Agent tool; it adds no data operation or mutation.

Paper depth is compressed for the tilted pile: ¥1k groups expose a 0.8px edge, ¥10k groups expose 4px, and higher groups are capped at 8px. Paper layers follow colors sampled from the supplied ¥100 note's lower edge, transitioning from red to peach across its width, with fine layer shading and light contact shadows. Three decorative note copies sit slightly out of alignment beneath each bundle's top face, with lateral offsets of at most 3.5px, vertical offsets within the existing depth and rotations below one degree. Fine shadows distinguish the exposed edges. Thin ¥1k groups use two copies and at most 2px lateral offsets. Flat bands occupy 12% of the note width, or 10% on thin ¥1k groups, and continue down the edge without a heavy border. The thin group preserves the source note's proportions. A merged ¥1k quantity badge does not multiply the depicted thickness.

Accounts (`#finance-accounts`) uses the shared Finance account and overview services. A pastel deck of real accounts remains the main visual, with swipe, Previous/Next, dots, and account chips for selection. One soft surface combines Net assets and this month's spending with the selected account's details, reducing repeated dividers. Add and Edit open a native mobile bottom sheet backed by the shared account save API; credit fields appear only for credit account types, and nature follows account type. Current balances remain transaction-derived and read-only; opening balance is editable. Loading, unavailable, and no-account states remain explicit. Account values come from live API responses, with no sample financial data.

Activity (`#finance-activity`) opens on the current local month, with previous/next controls, a year/month picker and Back to this month. Mint Income and blue Expenses summaries reuse the supplied money assets as exact CNY cash equivalents, followed by net cash flow and records grouped by local date. All, Expenses, Income and Transfers filters and merchant/category/account/note search narrow the list without changing the monthly summaries. Records retain their own currency labels; other currencies are excluded from the CNY piles without assuming an exchange rate. Transfers, including credit repayments, remain visible but do not count toward income or expenses. The Finance quick action opens a sheet for real CNY expense, income or same-currency transfer creation; record details support editing through the shared transaction services. Categories use a compact selected value that opens a searchable sheet with parent-category paths; account and date/time controls occupy full-width rows. Amount, category, active account, destination and local date/time are validated before saving; non-CNY records remain view-only. Expense entry offers One payment or Installments. Installments require an active CNY credit account, 2–60 payments, a first due date, total fees and a 1–12 month interval; the preview allocates exact cents with the remainder in the final payment and preserves the first due day's monthly anchor. The purchase is recorded once, then linked to the plan through the existing APIs. If plan creation fails after the purchase succeeds, its saved id and terms remain fixed and Retry installment plan adds only the plan. An existing unlinked credit expense can receive a plan without posting another expense; linked purchases open their plan instead of ordinary editing. Installment plans shows eligible CNY credit plans and each repayment schedule. A pending payment requires an active CNY asset account and an explicit Save repayment action; paid rows are disabled. Repayment failures preserve the selected account and note, and a confirmed payment stays paid if a later refresh fails. The shared list API caps each response at 200 records, so a capped month is loaded in bounded concurrent day requests. A capped or failed day is explicitly incomplete and withholds monthly/day totals. Loading, empty, error, stale refresh and unavailable lookup states remain visible; workspace/month request guards prevent old responses appearing in the new scope. These views reuse the existing `finance.transactions` Agent read capability and add no autonomous write tool.

## Workout

`/m/workout` is implemented in `src/mobile/pages/workout/index.tsx` and is available from both the bottom navigation and Apps directory. Its home layout adapts the supplied fitness dashboard: a compact date pill and oversized `Today, Workout+` headline, workout-progress strip, horizontal category capsules, and swipeable training-split tiles. Tiles show the latest recorded duration and date for each split, or an explicit no-session state; they do not imply an unstated duration goal. The bottom Body Metrics row expands to a two-tile Weight/BMI summary and a dark body-measurements panel. The activity tiles use project sky/mint colors in place of the source neon green and dark teal. Its cycle is Chest + Triceps, Back + Biceps, Shoulders, then Rest, repeating as three training days followed by one rest day. A configurable start date determines the current split day. The page records only one total duration per date and classifies it as Strength or Cardio. The initial view can show sample records; once a user saves an entry, the local workout record store replaces the sample set and persists the personal log on this device. These records are not exposed as a backend/Agent data capability.

Workout's Activity view (`#workout-activity`) follows the supplied Daily Activities reference separately from Overview: white canvas, a light Manrope two-line heading with a straight-stroke lowercase `y`, compact space before the equally aligned agenda/duration columns, pale-gray Weight and forest-green BMI cards, and a charcoal Body Composition panel with a lime measurement scale. The scale plots the supported waist value in centimeters; the reference's unsupported steps, heart rate and body-fat readings are not invented. Body opens the full measurements. Activity uses the standard shared greeting/date/search header without page-specific header typography or controls. Supporting Activity copy uses the Roboto Latin variable subset, with its SIL Open Font License in `public/fonts/roboto/`.

Body (`#workout-body`) shows a selectable front/back human illustration, with independent left/right limb measurements and a selector covering weight, height and 15 body dimensions. Recorded dimensions adjust a bounded illustrative silhouette; selecting a body area shows its current reading, dated change, Week/Month/Year trend and editable history below. An as-of date and optional previous outline support historical comparison. Trend points represent actual readings, and selecting a point updates the illustration and reading date. BMI uses a height recorded on or before the weight measurement and displays both source dates. Missing dimensions use a neutral shape; the illustration does not estimate body fat, muscle or actual appearance. The measurement dialog supports date, value, side and notes, with validation, editing and confirmed deletion.

History (`#workout-history`) provides Week daily bars, a Month calendar and Year monthly totals. Previous/next and Today controls navigate the period; Strength/Cardio filters update totals, charts and the session list together. Selecting a day highlights its record, and selecting a year bucket opens that month. Historical workout entry saves one total duration per date with its category and split; changing the cycle start preserves previously recorded splits. Empty periods offer a direct logging action.

The shared workout model and validation live in `src/services/workout/`; `src/mobile/hooks/use-workout-records.ts` subscribes to a workspace-specific browser-local store, shared by Home, Workout and quick entry. Sample data remains explicitly labeled and is removed from the personal log on the first save or Start my log action. Saved data is labeled On this device, persists across reloads and has no backend sync. Storage failures are reported rather than presented as successful saves. Agent exposure is excluded because these browser-local records are unavailable to the server runtime; any future backend integration must add identity-scoped persistence and separately evaluate Agent reads and confirmed writes.

The Body illustration shows the neck, torso and limbs with near-white flesh skin and separate pale-red muscle planes. The head is omitted from both the front/back illustration and comparison outline; head circumference remains available in the measurement selector. `BodyMuscles` follows the current chest and limb dimensions and provides distinct front/back regions below the surface highlights. Ivory highlights and neutral rose-gray shadows preserve the light skin tone. A translucent local measurement band and fine leader line connect the selected region to its reading; paired-limb labels follow anatomical left/right in both views. The previous-date comparison traces only the outer silhouette. These treatments remain local to Body and retain independent bounded deformation from recorded dimensions.

Its waist divides the illustrated height into 33% above and 67% below, following the requested long-leg proportions. The thigh and calf have near-equal lengths with a slightly longer calf and smooth knee/ankle transitions. `body-proportions.ts` projects the silhouette, surface details, measurement bands and hit regions together, keeping selection and historical comparisons aligned.

The lower half is an unboxed list with outline icons, supporting text, thin dividers and chevrons: Your apps, Cynexus Agent, Knowledge Base, Desktop workspace, and Sign-in & security. Desktop links restore the remembered destination. The settings gear opens and focuses the security disclosure; its two sign-out actions reuse the existing confirmation dialogs and authentication service. No profile-edit API, activity metrics, follower counts or session counts are fabricated.

## Metric entry preview

The shared bottom-navigation `+` menu exposes Weight, Body and Workout actions. Each opens the shared `src/mobile/components/metric-entry/` overlay, which reproduces the supplied dual-wheel composition: two complete gray circular bands clipped by the canvas into opposing semicircles, numbers following concentric circular paths, a yellow center marker, red top and Add controls, and circular switch/cancel actions. The circles and numbers scale together with the content width; the selected values and colon share one horizontal line. Each half supports independent touch/mouse dragging with continuous movement and snapping on release, mouse-wheel scrolling, number taps and arrow/Home/End keys. The left circular action cycles between the three metric modes; the right action cancels the current add. The wheel ranges and the centered unit label change with the mode (`kg`, `cm`, or `hr · min`). Weight and waist use the shared model ranges in 0.1 increments; duration supports 00:01–24:00, with Add disabled for 00:00. The maximum whole value fixes the fractional/minute wheel at zero. Workout and body entries are written to the existing on-device workout record store so the Workout views update immediately; there is no backend sync yet. Body currently records the selected value as waist circumference, matching the existing body summary. A future broader metric service must replace this preview and evaluate Agent exposure separately.

Metric entry uses static 600/800 instances of the existing licensed Manrope face, scoped to the overlay. This keeps its button labels and bold selector values consistent in WebKit environments that display the variable face's default thin outline despite the requested weight; the shared mobile font remains unchanged.

## Migration rule

Move a high-frequency workflow one complete path at a time: list, detail, edit, save, error, and return. Put the page under the owning feature's `mobile/` folder once it has its own interactions. Extract API calls, calculations, and validation to shared services/hooks instead of copying them between desktop and mobile.
