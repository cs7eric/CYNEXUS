# Findings

## Current State

### 2026-08-16 Follow-up: as-of consistency and flexible patterns

- The normal Screener obtains quote and multi-period returns from ClickHouse using a fixed 400-calendar-day window, solely so the response can always include a 252-session return. It does this even when the active criteria require only short-horizon measures.
- The UI sends no date by default. The ClickHouse query then selects its latest available trading date, but the UI does not make the requested-versus-actual fallback prominent.
- The visible snapshot date is the ClickHouse quote date. Industry has a shared latest-on-or-before snapshot, fund flow falls back per stock, concept/style membership has no historical date bound, and the PostgreSQL daily-fact pattern query falls back to its own latest date. This permits mixed-date rows while displaying just one date.
- The initial correction will make indicator history window demand-driven and treat a missing exact-date technical fact as unavailable rather than calculating a pattern from a stale prior date. Historical concept/style data cannot be made point-in-time correct without a snapshot schema, so it must be surfaced as current classification rather than silently represented as historical truth.
- The current board condition is a single inclusive board value. Supporting the requested default requires explicit exclusion flags for ChiNext and STAR rather than overloading the existing board selector.
- Current volume-contraction logic is a strict monotonic consecutive-volume sequence and the current volume criteria are lower bounds only. Approximate natural-language volume semantics need explicit upper bounds, with the AI proposing editable ranges instead of declaring a precise multiple mandatory.
- The current durable OHLCV fact supports deterministic daily candlestick forms: bullish engulfing, hammer, doji, and long bullish candle; it also already supports 20-session high breakout and trend/volatility conditions. Multi-swing patterns such as double bottom, head-and-shoulders, cup-and-handle, and flags require a longer, quality-assured historical series plus explicit swing-detection policy and are not part of this change.

- `stock_selection_ai_intent_planning` already returns a bounded `criteria` map plus rules, assumptions, unsupported phrases, and warnings.
- The market Screener supports a broad basic catalogue and one typed `priceVolumePattern` (contraction days, breakout-volume multiple, bullish body) backed by bounded daily OHLCV history.
- The required delivery is to make this planning result unmissable in the UI and extend the typed criterion catalogue with additional data-backed patterns.
- The AI policy validates only a flat scalar allow-list. It needs to evolve in lockstep with the market query contract so model output, UI controls, and the hard filter accept exactly the same criteria.
- The current UI already has an AI-plan application callback, but it only maps the three existing price-volume fields. All other planned criteria are silently unavailable to the condition builder, which explains the perceived lack of executable AI output.
- The Screener repository obtains a trusted full-market daily snapshot and conditionally joins only the recent history needed for the existing pattern. Additional technical criteria should reuse this bounded read path and avoid any AI-generated query logic.
- The durable daily fact has `open_price`, `high_price`, `low_price`, `close_price`, `prev_close`, `volume`, and `amount`, so moving-average alignment, new-high breakouts, volatility contraction, candlestick-body/range and volume confirmation can be derived without introducing an untrusted data source.
- The UI condition builder exposes only one dedicated technical-pattern section. The AI plan result needs an explicit plan-review state that shows every mapped indicator before it mutates the builder or starts screening.
- The current AI panel has separate `Interpret` and `Run` actions, but applying a plan exposes only the descriptive rules and maps three fields. It does not render an auditable indicator/value list, nor does it return the user to the indicator builder for editing. This is the precise workflow gap to close.
- The technical expansion can be bounded to the existing daily fact: close-vs-MA20, MA5-vs-MA20 spread, N-session high breakout, ATR20 volatility ceiling, consecutive bullish candles, and current-volume-vs-MA5. Each is deterministic and can be rendered as an editable numeric control.
- The Market controller/app service currently expose the three pattern values as flat query parameters, then build `PriceVolumePattern`. The extension must be propagated through this API boundary, DTO, query BO, domain policy, repository, agent schema, AI allow-list, and UI service before it can be called executable.
- Saved user strategies and the autonomous `market.stock_screener` read path use the same typed market contract. The extension must preserve these consumers by serializing every added criterion into strategy replay and the bounded Agent schema.
- The AI candidate adapter calls the typed Market Feign API rather than constructing data itself, so extending the Feign contract is required for AI-proposed technical criteria to become hard candidate filters.
- Runtime coverage is currently 30 trading sessions (2026-07-06 through 2026-08-14). MA20 and ATR20 are supported now, but a configurable 120-session high breakout would silently have incomplete coverage. The delivered criterion must either cap the lookback at the verified 20-session window or add a governed historical backfill before claiming the 120-session range.
- Runtime validation exposed a semantic quality failure in the v1 intent plan: the provider returned `volumeContractionDays=2` and labeled supported phrases (`持续缩量`, `三倍爆量`, `大阳线`) unsupported. The v2 prompt and domain reconciliation now guarantee that these supported phrases become editable minimum criteria: at least three prior shrinking sessions, explicit 3x volume, and a 4% body plus 5% daily-change threshold. The model still supplies the broader plan; the domain policy prevents a weak/contradictory plan from reaching the execution stage.
