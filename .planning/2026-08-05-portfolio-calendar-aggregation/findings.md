# Findings

## 当前发现

- 根目录已有其他任务的 task_plan.md、findings.md、progress.md，本任务使用独立 `.planning/2026-08-05-portfolio-calendar-aggregation/` 目录，避免覆盖用户已有记录。
- CodeGraph 初始发现索引存在待同步修改，已执行 `codegraph sync`。
- 日历图组件只是展示 API 返回的 `point.periodPnl`；周/月/年聚合由 `PortfolioPerformanceDomainService` 完成。
- `PortfolioOverviewAppService.performance` 在交易时段会把“当前日期”的 `todayPnl` 覆盖到返回点。周/月/年返回点的日期也是当前周期最后交易日，因此该逻辑会把整个周/月/年收益错误替换成单日收益。
- 聚合服务在请求价格序列中已包含当日实时价格，当前聚合点本身已经包含当日收益；覆盖逻辑只应适用于日粒度。
- 当前 Release `/api/market/portfolio/overview` 返回持仓 `todayPnl: null`，导致 UI `PortfolioReturnBreakdown` 在 `mode="today"` 下过滤掉全部持仓并显示“暂无可用的当日持仓收益数据”。
- `overview()` 在收盘后加载了日线/分钟行情，但调用 `calculateTodayPnlBySymbol` 时把 `latestPrices`、`previousClosePrices`、`realtimePriceDates` 和分钟行情全部替换成空 Map，直接丢失了可用的当日价格。

## 2026-08-06 复核

- Release 当前日接口的可见点收益为 `12.1 + 93.3 + 91.2 + 0 = 196.6`，周/月/年接口都只返回 196.6；这只覆盖了 2026-08-03 之后的基线区间。
- `latestResetAt` 被错误地同时当作收益视图起点，导致月视图虽然请求全年、年视图虽然请求五年，但后端先把 `from` 截断到 2026-08-03，视图内更早交易日无法参与聚合。
- 收益基线只应影响 realized P&L 的校准，不应裁剪用户请求的性能视图范围；聚合应对请求范围内产生的 daily points 求和。

## 2026-08-06 视图收益与总资产复核

- `PortfolioReturnBreakdown` 仍按当前持仓的 `unrealizedPnl` 绘制 Treemap；这与周/月/年视图的 `performance.points[].periodPnl` 无关，导致图块表达的是持仓贡献而不是视图涨跌。
- `PortfolioPerformanceDomainService.snapshot` 原先对所有历史日复用当前 `availableCash`，因此总资产会随历史持仓市值和买卖名义金额跳变，不能反映每日收益路径。
- 历史现金应从当前可用资金反推：对快照日之后的确认交易反向还原买入/卖出现金流，再与该日收盘持仓市值相加。

## 2026-08-06 最终 Release 复核

- 当前月窗口（2026-08-01 至 2026-08-06）日点为 `-61.89999、93.3、91.2、0`，总计 `122.60001`；周聚合点同为 `122.60001`。
- 该窗口的总资产从 `12269.60999` 变为 `12392.21`，与收益点累计变化一致。
- 年/月窗口的聚合点也满足 `periodPnl = 视图内日点之和`；热力图组件只读取 `performance.points[].periodPnl`，不再读取当前持仓浮盈。

## 2026-08-06 用户口径纠正

- 热力图的正确节点是证券/持仓，数值是该证券在当前日/周/月/年视图区间内累计贡献的收益；日期点只用于计算与聚合，不能直接作为热力图节点。
- 7 月 30 日出现约 `-3062.85` 的直接原因是 `dailyPoints` 最近从按证券计算日收益改成了历史总资产差额；首次导入持仓日因此把导入成本与当日行情之间的历史差额误记成了当天收益。
- 领域服务原有 `calculateTodayPnlBySymbol` 已明确将最早交易日视为导入基线日并返回 0；使用资产差额绕过了这条基线规则。
- 8 月 3 日当前的 `-61.89999` 也是资产差额口径带来的结果；按原有逐证券日收益算法应使用前收、当日成交和收盘价计算，并由各证券贡献相加。
- 总资产曲线应以同一套逐证券收益累计形成，保证相邻点 `totalAssets` 差额等于该日 `periodPnl`，同时以区间末日真实资产倒推历史点。
- 用户截图中的正确视觉结构仍是证券矩形块（代码、名称、收益金额），错误只在金额口径：应从当前持仓浮盈改为该证券在所选视图区间内累计产生的收益贡献。
- `PortfolioPerformanceDTO` 当前没有逐证券贡献字段，必须从领域计算结果向 API 增加 contributions，再由 UI 绘制，不能由前端用日期点或当前持仓浮盈猜算。
- 账户只保存当前总资产，没有独立的历史入金/出金流水；因此历史总资产应由当前总资产按逐日收益向前倒推，保证同一日期在不同视图中的资产值一致。

## 2026-08-06 口径返修 Release 复核

- Release 日视图中 2026-07-30 收益为 `0`，首次导入持仓只作为基线，不再产生约 `-3062.85` 的伪亏损。
- 2026-08-03 日收益恢复为 `12.1`；后续日点为逐证券前收、成交与收盘价计算结果，不再使用历史资产差额替代收益。
- 日/周/月/年接口的 `contributions[].periodPnl` 求和均与对应视图 `periodPnl` 完全一致，节点为证券代码和名称。
- 日视图每个相邻 `totalAssets` 差额均等于当日 `periodPnl`，历史资产路径与同一套逐日收益计算保持一致。

## 2026-08-06 日视图热力图复核

- `contributions` 过去无条件使用 `periodPnlBySymbol`，日视图因此把近一个月的累计贡献直接绘制为当日热力图。
- 日粒度现使用 `lastDayPnlBySymbol`；交易时段中以实时的 `todayPnlBySymbol` 整体替换该日历史贡献。周/月/年继续使用区间累计 `periodPnlBySymbol`。
- Release 核对时日视图 `todayPnl = -6.2`、热力图贡献合计也为 `-6.2`，而近一个月 `periodPnl = 354.9`；周视图贡献合计仍等于周收益 `190.4`。
- 日历日期现在使用真正的按钮交互；有交易点的日期可选，无交易数据日期禁用。选中历史日期后前端请求 `range=daily&from=日期&to=日期`，右侧热力图与当日摘要使用该单日结果。
- Release 实测选中 2026-08-03 返回 `periodPnl = 12.1`，逐证券贡献合计同为 `12.1`。

## 2026-08-06 动态总资产

- `portfolio_account.total_assets` 当前是手动输入的固定基线，`PortfolioAccountDomainService.totalAssets()` 直接返回该值。
- `updated_at` 已记录手动输入时间，可作为收益累计起点；动态结果不应回写该字段，否则会重复累计。
- 当前性能领域服务已经能按交易日计算逐证券收益，因此动态总资产应使用“基线 + 输入日期之后的逐日收益”，并让 performance 的末日资产使用同一结果。
- 为避免把手动输入时刻已经包含的当天波动重复计算，本次按手动输入所在本地日期作为基线日，从下一交易日开始累计。
- Release 验证：手动基线 `12392.21`（2026-08-04），累计 2026-08-05 `+91.2` 与 2026-08-06 `-6.2` 后，overview/account 当前总资产均为 `12477.21`。
