# Findings

- Live `cynexus.ch_dwd_kline_1m` stores OHLC, amount, and volume; it does not store turnover rate or volume ratio.
- Live `cynexus.ch_ods_stock_timeshare_1m` includes price, average price, volume, turnover, turnover rate, and volume ratio, but currently contains zero rows.
- Existing normalized `volume_ratio` is an adjacent-minute comparison rather than the standard market volume-ratio definition, so it must not be part of the new chart/cache contract.
- The existing trade-review implementation already consumes stock chart, industry/index overlay, market-indicator replay, review anchors, and local TDX 1m load capabilities.
- Current sizing baseline for the latest inspected trade date is roughly 2,316 unique timeshare series and 555,840 minute points per day after stock/industry/index selection and deduplication.
- Redis integration must go through `cynexus-common-cache`; feature-specific cache mapping/fallback belongs in market `infra/cache`, while domain/application code must not know Redis keys or clients.
- Redis is explicitly non-authoritative: cache miss, corruption, or Redis failure must fall back to ClickHouse.
- A new raw interactive timeshare endpoint is unsuitable as an autonomous Agent tool because it is UI-oriented and potentially large. Any future Agent exposure should be a separate bounded summary capability rather than raw minute-series access.
- Backend business rules such as selection, ranking, as-of filtering, completeness, and fallback belong in the market domain layer; application services only orchestrate and map DTOs.
- The existing stock-chart API already models `timeshare` on `StockChartBO`/`StockChartDTO`; the new durable/cache path should implement the existing chart gateway contract where possible instead of introducing a second incompatible chart payload.
- The trade-review page already caches its data-health probe in browser localStorage for eight hours on the same trade date; server-side timeshare cache freshness must remain independent from that UI probe cache.
- `cynexus-common-cache` currently exposes string-oriented `RedisCacheOperations`; true compressed binary values will require a deliberate shared-module byte-array operation/serializer extension. Base64-wrapping compressed payloads would add roughly 33% avoidable overhead.
- The existing Python `sync_tdx_intraday_detail` job already supports explicit code lists, trade date, provider selection, checkpoint/resume, ignore-errors, batch writes, and a dry-run path. Its current default, however, expands to all active securities and must not be used unchanged for the selective policy.
- The Data Executor `/tdx/timeshare` endpoint currently calls `easy_tdx` directly. The trade-review UI also has direct Easy-TDX fallback paths, which explains repeated per-card network latency and must be removed from the steady-state serving path after durable storage is populated.
- `ClickHouseStockChartClient.listTimeshare` and the existing `/api/market/stock-chart/intraday` contract already read `ch_ods_stock_timeshare_1m`; a cache adapter should be inserted behind the market repository/gateway rather than added directly to the controller or UI.
- Correction after reading the live SQL resource: `ClickHouseStockChartClient.listTimeshare` is currently named as a timeshare read but actually reconstructs price/VWAP from `ch_dwd_kline_1m`. The implementation must switch this SQL to `ch_ods_stock_timeshare_1m`; otherwise the product would still silently use reconstructed 1m K data.
- The current THS constituent snapshot already contains `snapshot_date`, `industry_code`, `stock_code`, `rank`, `change_pct`, `turnover_pct`, and related close snapshot fields. The selective collector can use this durable daily snapshot as its industry membership/ranking input rather than re-calling THS during collection.
- Existing `market_limit_daily_stocks` provides explicit `limit_up`/`limit_down` categories and supports both 10% and 20% boards without hard-coding a single threshold.
- A complete replay guarantee requires adding same-day portfolio trade symbols to the mandatory selection pool. These are tenant/principal-scoped in `cynexus_appl_market.portfolio_trade`; the Data Executor must receive only the deduplicated symbol list, not user identity or trade details.
- The existing scheduler only uses `sync_tdx_intraday_detail` for auction-oriented jobs. The post-close timeshare archive should be a separate scheduler code/policy, not overloaded into `kline_1m_tdx_close` or auction refresh jobs.
- The daily screening fact contains `close_price`, `prev_close`, `change_pct`, volume, amount, and turnover rate; it is suitable for close-based sorting and metadata enrichment, while explicit limit status should still come from `market_limit_daily_stocks`.
- `easy_tdx.get_history_minute_time_data` feeds the current normalized timeshare rows. The normalizer currently hard-codes `source="eltdx"` even on the Easy-TDX path and persists `raw_payload`; the new contract must propagate the real provider and omit raw payload from the chart fact.
- Current source normalization already produces `price`, `avg_price`, `volume`, and `turnover`. These are the only point-level chart fields needed by the new persisted/cache contract.
- Live probes of both Easy-TDX and eltdx for `600519` on `2026-08-07` returned exactly 240 points but only meaningful `price` and `volume`; `avg_price` was null and `turnover` was zero. Therefore a complete solution cannot claim the source currently provides an accurate average-price line or turnover amount.
- The chart fact should treat raw timeshare price/volume as authoritative. Accurate VWAP/turnover requires either provider decoder enhancement or minute-aligned enrichment from `ch_dwd_kline_1m.amount`; this enrichment must be explicit and must never replace the raw timeshare price series.
- eltdx exposes a `minutes.recent` protocol that includes `avg_price`, but live date-specific probes returned zero points while the no-date call returned 240 points mislabeled with the current weekend date. It is not reliable enough for the first production version without a separate decoder/date-selector fix.
- Deterministic first-version enrichment should therefore use raw historical-timeshare price/volume plus exact minute `amount` from local 1m K to compute turnover and cumulative VWAP. This is enrichment only: raw timeshare remains the displayed price source, and the system must label the lineage as `timeshare+tdx_1m_amount`.
- Live comparison for `600519` showed exact minute alignment: raw timeshare volume `630` lots corresponds to local 1m K volume `63,000` shares, and 1m K provides nonzero exact amount. The enrichment must normalize volume units explicitly (`lots * 100 = shares`) before reconciliation.
- Easy-TDX historical timeshare returned 240 points for the Shanghai Composite (`sh000001`) but returned zero points for tested industry codes `880380` and `881273`. Industry context therefore cannot rely on the stock historical-timeshare protocol.
- This matches the product requirement that index/industry context may be an intraday K chart: stock/ETF uses raw timeshare, while index/industry uses existing `ch_dwd_kline_1m` as its durable fact and only shares the normalized Redis/API chart payload. Do not duplicate index/industry 1m K rows into the stock timeshare table.
- Easy-TDX raw timeshare uses minute-start labels (`09:30` through `14:59`), while local 1m K uses minute-end labels (`09:31` through `15:00`) for the same 240 observations. Amount enrichment must align by canonical session slot or shift the K timestamp by one minute; joining the raw timestamps directly would be wrong.
- Canonical replay storage should use minute-start slots: `09:30–11:29` and `13:00–14:59`. The chart axis can still display the full `09:30–15:00` session, and trade/indicator timestamps map by floor-to-minute.
- CodeGraph impact shows changing the existing string `RedisCacheOperations` affects multiple AI, WeChat, and market consumers. Add a sibling `RedisBinaryCacheOperations` instead of changing existing method semantics.
- Python already has a shared Redis hook, but it forces `decode_responses=True`. Add an explicit binary-client method/option for the timeshare producer rather than bypassing the hook or base64-encoding values.
- Cache insertion can remain entirely in infrastructure: Python publishes the immutable binary value after ClickHouse persistence succeeds; market `infra/cache` reads it and falls back to the existing durable repository. The domain repository interface does not need Redis-specific methods.
- The scheduler resolver has distinct close-time 1m K and auction jobs. The new archive entry can reuse the same Data Executor job runner but needs a new code such as `trade_review_timeshare_close` with a dedicated selection phase.
- Live verification showed the remaining throughput bottleneck is the per-target synchronous `ALTER TABLE ... DELETE` in `ClickHouseTradeReviewTimeshareSink.replace`; no per-target `ch_dwd_kline_1m` SELECT remains.
- The current target table is reused by trade date, so its READY/FAILED counts are aggregate across retries. Redis key count is the reliable cache-progress metric.
- Beijing 920xxx symbols require BJ normalization; mapping them to SZ produces empty TDX history responses.
- Batch cleanup verification: the optimized run issued one archive-scope ClickHouse DELETE (~3.1s) instead of one DELETE per target; subsequent target writes no longer generate per-target mutations.
- Source profiling found a second major bottleneck: `easy_tdx.TdxClient.from_best_host()` pings every known endpoint for every symbol while holding the shared factory lock. The archive now reuses easy_tdx's persisted best host and only falls back to probing when no best host is available.
